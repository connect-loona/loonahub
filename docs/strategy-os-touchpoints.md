# Strategy OS touchpoints — legacy implementation inventory

Generated by reading `strategy-app.js` end to end (the Step 2 extraction of Strategy OS's
former inline implementation out of `index.html` — see that file's own header comment).
This is the spec the working-instructions doc's Step 2 exists to produce: every point
where the legacy implementation touches something outside itself, so the new React app at
`apps/strategy/` can deliberately replace each one instead of inheriting it by accident.

`strategy-ui.js` — a separate file, loaded independently via `app.js` — is a second,
smaller layer sitting on top of the same page. It's covered here too since it depends on
several of the same touchpoints.

## How it loads and starts

- `index.html` loads `strategy-app.js` via a plain `<script src="strategy-app.js">` tag,
  in the same position its code used to sit inline.
- `app.js` (a separate, tiny file, loaded early) dynamically injects `strategy-ui.js` as a
  deferred `<script>` — a decorator that runs after the fact and patches the DOM further
  via a `MutationObserver`. `strategy-app.js` has no idea `strategy-ui.js` exists; the
  dependency runs one way, from `strategy-ui.js` onto `strategy-app.js`'s output.
- Entry point: `soOpenPage()`, called from index.html's own tab-navigation click handler
  (`if (typeof soOpenPage === 'function') soOpenPage();`) when the "Strategy OS" nav
  button is clicked. This is the one genuine "outside code calls into this file" edge —
  every other `window.so*` export exists only so this file's own generated HTML can wire
  up `onclick="..."` attribute handlers, which run in global scope by nature.

## Globals it reads (owned by index.html, defined outside this file)

- **`currentUser`** — the display name of whoever is "logged in" via Hub's simple
  profile-picker system (a plain in-memory string set by `index.html`'s `login(name)`,
  itself triggered either by picking a profile pill or, per that function's own comment,
  automatically on every `firebase.auth().onAuthStateChanged` firing with a matching
  email). Read in ~10 places — used as the acting-user name on writes (task assignment,
  archive/restore attribution, learning-event actor).
- **`_db`** — the shared Firebase Realtime Database client reference `index.html`
  initializes once at startup. Used in ~22 places for both listeners (`.on("value", ...)`)
  and direct writes (see "Direct Firebase access" below).

Notably: **no shared CSS-selector-scoped helpers, no shared DOM-building utilities.**
Every rendering helper this file uses (`esc`, `fmtDateTime`, `monthLabel`, `soWorkingDots`,
`statusLabel`, `STAGE_LABELS`, `STAGE_ORDER`, and ~65 others) is defined inside this same
file — confirmed by cross-referencing every identifier this file calls against the ~72
functions it defines itself. The two globals above are the entire external-read surface.

## Globals it writes that something else reads

- **`window._soRunsCache`**, **`window._soBrandsCache`** — the live Firebase snapshot
  caches for the run list and brand list, kept current by this file's own listeners.
  `strategy-ui.js` reads both to build its decorated rail/workspace UI.
- **`window._soCurrentRun`** — the currently-open run's live snapshot (`null` when on the
  list view). `strategy-ui.js`'s own comments call this "load-bearing": it reads this
  global directly to build the numbered stage rail and review sidebar.
- **`window._soBrandView`** — read by `strategy-ui.js`, but never actually written to
  `window` by this file — it's a plain module-local `var _soBrandView` here (line 106).
  That read in `strategy-ui.js` always resolves to `undefined`. Pre-existing, unrelated to
  this extraction (confirmed unchanged from the exact inline code this file was extracted
  from) — noted here as a real quirk of the legacy implementation, not something to carry
  forward deliberately, and not something this step fixes.

## Its own public API surface (`window.so*`, 30 functions)

All 30 are attached to `window` purely so this file's own generated `onclick="..."` HTML
attributes can reach them (attribute handlers execute in global scope). Two are also
called from outside this file:

- `soOpenPage()` — the real entry point, called by index.html's nav click handler (above).
- `soBackToList`, `soCloseNewRunModal`, `soOpenNewRunModal`, `soOpenRun`, `soReopenStage`
  — also called by `strategy-ui.js`'s decorated UI (its numbered rail's "click a done step
  to reopen it" affordance, its own back-to-list button, etc.).

The other 25 (`soArchiveRun`, `soRestoreRun`, `soPurgeRun`, `soDecide`, `soRetryStage`,
`soCreateTeamTasks`, `soUpdateDeckPage`, `soSuggestSimilar`, `soToggleRefineBox`,
`soSendRefine`, `soDiscardConcept`, `soAcceptConceptCandidate`, `soRejectConceptCandidate`,
`soRetryConceptCandidate`, `soReplaceCopyAsset`, `soToggleAssetLock`, `soOpenBrandList`,
`soBackToRunsFromBrands`, `soOpenBrandForm`, `soAddAudienceRow`, `soAddPillarRow`,
`soSubmitBrandForm`, `soSetRunListView`, `soSubmitNewRun`) are called only from this
file's own generated markup — self-referential, not a real cross-file boundary.

## DOM it depends on from outside itself

Exactly one: **`#so-root`**, the mount point `<div>` that lives in `index.html`'s static
markup (outside the Strategy OS block). Every other element ID this file reads or writes
(`so-new-run-modal`, `so-bf-name`, `so-stage-rail`, dozens more) is namespaced `so-` and
created by this same file's own template strings — there is no other reach into markup
this file doesn't itself own.

## Direct Firebase access (the doc's flagged "known issue, separate track")

The working-instructions doc is explicit that the new app must go through Netlify
Functions for writes, never Firebase directly — "the legacy Hub writes from the browser,
which means Firebase security rules are the only thing protecting that data. The new app
does not extend that pattern." Here is every direct `_db.ref(...)` call this file makes,
for the new app to replace with a real backend endpoint:

| Path | Operation | Used for |
|---|---|---|
| `strategy_brands` | listen | brand list + names shown in run table/New Run picker |
| `strategy_runs` | listen | the run list |
| `strategy_runs/<runId>` | update | archive (sets `archivedAt`/`archivedBy`/`archiveReason`) |
| `strategy_runs/<runId>` | update | restore (clears those three fields) |
| `strategy_runs/<runId>` | remove | permanent purge |
| `strategy_runs/<runId>` | listen | the open run's live detail view |
| `strategy_runs/<runId>` | read once | building per-deck-page tasks |
| `tasks` | push | one Hub task per deck page ("Create team tasks") |
| `strategy_runs/<runId>` | update | stamps `teamTasksCreatedAt` after the above |
| `strategy_runs/<runId>/stages/deck-builder/checkpoint/pages/<i>` | update | editing one deck page's fields |
| `strategy_runs/<runId>/stages/<stage>/candidates/<assetId>` | remove | discarding a refine candidate |
| `strategy_runs/<runId>/stages/<stage>/locks/<assetId>` | read/write | per-asset lock toggle |

All the actual pipeline-advancing writes (approve/reject a stage, start a run, propose an
asset refine, accept/reject a candidate, reopen a stage) already go through Netlify
Functions (see the endpoint list below) — the table above is the direct-write surface
that's genuinely left to close, matching the doc's own framing of this as real but
separate, not-this-rewrite's-job work.

## Backend endpoints called directly (`fetch("/.netlify/functions/...")`)

- `strategy-run-start`
- `strategy-stage-approve`
- `strategy-stage-retry`
- `strategy-stage-reopen`
- `strategy-concept-propose`
- `strategy-concept-accept`
- `strategy-concept-discard`
- `strategy-brand-save`
- `strategy-deck-download`

All nine already exist as their own Netlify Functions (`netlify/functions/strategy-*.js`)
and are reusable as-is by the new app — they're already the "shared backend" layer the
target architecture calls for. The new app authenticates its own calls to these with an
ID token from its own Firebase Auth init (see `apps/strategy/src/firebase.ts` and the
Step 1 spike) rather than `strategy-app.js`'s current cookie-based session check.

## Shared CSS classes this file's rendered HTML currently depends on

Hub-wide utility classes (defined in `index.html`'s global stylesheet, used by every tab,
not Strategy-specific) — the new app must not reuse these selectors, per the working
doc's boundary rule:

`btn`, `btn-ghost`, `btn-primary`, `form-control`, `att-board`, `att-tbl`, `bh`, `note`,
`tag`, `section-title`, `section-header`, `scroll`, `wide`

Strategy-specific classes (also defined in the global stylesheet, but scoped to Strategy
OS's own markup): `so-row`, `pf-absrow`, `so-working`, plus the `so-*` classes used
throughout its own rendered elements.

## What this means for `apps/strategy/`

Every touchpoint above needs a deliberate replacement, not an inherited one:

1. **`currentUser`** → the new app's own Firebase Auth user (already proven reachable —
   Step 1's spike). No global to read; use `onAuthStateChanged`/the current user object.
2. **`_db` direct reads/writes** → the run-list/run-detail listeners can stay Firebase
   reads (that's normal client-side Firebase usage, not what the doc's write-path rule is
   about) but should go through the modular SDK, the new app's own init — never the
   legacy `_db`. The direct-write table above needs actual new endpoints (or extending
   existing ones) rather than being carried forward as browser-side writes.
2. **`window._so*Cache`/`window._soCurrentRun`** → ordinary React state/a store
   (Zustand or similar, per `apps/strategy/src/stores/` in the target layout) — no globals.
3. **`#so-root`** → N/A; the new app owns its whole page at `/strategy/`, no shared mount
   point with legacy markup.
4. **The 9 backend endpoints** → called as-is, with the new app's own ID token.
5. **Shared CSS classes** → replaced by the design tokens from Step 3, not reused.

`strategy-app.js` and `strategy-ui.js` both stay live and unmodified through this — they
remain the "legacy Strategy OS" the rollback plan keeps reachable for a month after the
new app ships.
